# 开放任务系统

任务无需接受，普通任务可以任意顺序完成；推荐顺序为 `docs/quests.json` 的数组顺序。中央“工厂”页签右侧是“任务”；待完成包含已开放的未达成和已达成待领奖任务，已完成仅列已领取奖励的任务。达到后永久保留，安装、消耗、拆除设备不会撤回；进入后续阶段仍可领取前期任务奖励。

## 阶段终局与推进

- P1～P5 各一项 `stage_final: true` 的终局任务。唯一阶段推进条件为完成并点击领取该终局任务奖励；只制造里程碑物品、达成但未领奖、普通任务领奖或开发者下单开关均不推进。里程碑继续记录真实首次制造并用于配方前置，P6 首次制造智能机器人的主目标保持，不存在 P7。
- 终局开放门槛为同阶段非终局任务数的一半向上取整：8 项需完成 4 项，9 项需 5 项；只统计 `completed` 中已达成的普通任务，未领奖也计入，不计算其他阶段或终局本身。0 项普通任务时门槛为 0。
- 未到所属阶段或不足门槛时不在待完成列表 / 数量 / 待领奖红点中显示，也不新记终局达成或通知；运行层再次检查开放条件，不能直接调用领奖绕过。先制造目标、后完成半数任务时无需重复制造，达到门槛的同一转换即可记达成。普通任务先判定，再判定终局，与配置推荐顺序无关。
- 终局卡片使用静态粉色描边 / 轻阴影和“阶段终局任务”标签，明确“完成本任务并领取奖励后解锁 Pn 阶段”；隐藏时提供匿名门槛进度提示。已领奖终局在已完成列表保留，即使后来追加普通任务、门槛提高也不回退阶段。
- 当前共 13 项：P1 八项普通任务与终局，以及 P2～P5 四项终局。P2～P5 暂沿用原里程碑制造目标；尚未配置普通任务，因此暂不要求量产线或数量证明。后续任务线在此基础上追加，门槛自动重算，不将本次框架写成已实现量产考核。

## 判定、领奖与存档

- `obtain_item` 使用永久获得记录 / 制造记录，当前只支持首次获得（count=1），不要求道具仍在仓库。制造到机器产物缓存也算获得，但查看图鉴 / 切换配方不算。
- `workshop_recipe` 使用实际工作室批次数；只在成功交付单批产物时加一。开工、取消、暂停、满产物上限等待和地图机器执行同配方都不计数。每种已完成工作室配方的批次数有安全整数上限，支持以后配置累计批次任务。
- `automated_delivery` 的 target 为 bus，累计实际固体 / 流体物流及机器人正常卸货进入 WH 的件数，主厂 / 分厂均有效。堵塞、失败、手动拾取 / 收取、手工生产入仓及取消退款不计；真实成功转移才更新 `automated_received`，不依赖动画或当前仓库有无库存。
- `craft_item` 使用永久 crafted 制造记录，当前首次制造 count=1，不以获得 / 奖励 / 拆回代替。I0060 保持原编号与配方，更名流水线机械手；制造后停留 P1，普通任务达成至少 4 项后可完成并领取 p1_free_hands，开放 P2 与下单，不消耗本体。其后同样只由阶段终局领奖推进。`stage_2` 是 P1 原机制标记，不能挂在普通任务上；所有新阶段统一由 `stage_final` 表达推进。订单细则见 [warehouse-orders.md](warehouse-orders.md)。
- `industry.quests` 只存在于主厂：completed / claimed 唯一 ID 数组、workshop_batches 配方计数、automated_received 入库累计与可选 `stage_quests_version: 1`。新进度写入版本 1，阶段由依次已领奖终局推导；客户端与 Go 均拒绝只靠制造里程碑抬高的新版本 stage。完整本机 / 云存档、增量快照携带同一账本；其他厂区仅投影显示，无副本。
- 缺 `stage_quests_version` 的旧档先按原制造 / P1 领奖规则只读校验，再由客户端克隆升级：仅补认 `tier < 已有 stage` 的终局 completed / claimed，保留原阶段并写版本 1，不补普通任务、不发物品、不代领当前阶段终局；以后推进必须走新规则。旧 P1 已领奖依然有效。更早缺 automated_received 的存档仍沿用原 P1 机制兼容。读取 / 云恢复前建立升级后基线，不触发历史气泡或剧情；服务端验证兼容旧格式但不修改上传内容，无数据库迁移。
- `claim_quest` 是 Worker 世界操作，在克隆后的完整世界中校验任务已达成且未领取，然后将全部奖励加入起始厂仓库、记录 claimed。同一世界串行处理，重复领取或任一奖励溢出则整笔拒绝。可在任何厂区查看 / 领奖，奖励不会进入当前分厂；查看任务不改变库存，奖励不计入 crafted、生产统计、制造解锁或行业里程碑。
- 新的达成事件由主线程运行时对确认快照作差，按顺序显示每条 3 秒的底部气泡，不阻止编辑；气泡关闭不影响未领奖红点。通知最多保留最近 20 条，仅是本次会话的展示数据，不写存档。首次读取的补认和主动云恢复不重播历史通知；红点仍显示实际待领取状态。
- 客户端与 Go 校验已知任务 / 配方编号、唯一数组、claimed 是 completed 子集、整型计数与大小边界；拒绝 null / 未知字段。服务端继续只校验存档结构，不证明单人任务真实性，无新数据库迁移。

## 后续扩展

在 `docs/quests.json` 追加稳定 ID、阶段、标题、说明、目标及奖励。获得目标与奖励使用现有物品全名（包括“设备·”前缀），工作室目标使用小写配方 ID；`npm run import:gameplay` 解析为运行 ID 并生成目录，不能手改生成的 definitions.json，也不修改原始 v0.9 设计案。既有 ID 不复用、不移除，已有领奖记录不因更新配置再次发奖。任务奖励不作为工业静态闭包的可用材料。

配置可选 unlocks 保存已支持的机制奖励；终局隐含下一阶段奖励，因此 `stage_final: true` 时 rewards 也可为空，不虚构奖励物品。导入器拒绝重复终局、P6 以后推进和非布尔标记，并要求 P1～P5 各有一个终局。按物品 / 按设施的自动化产量和材料提交尚未支持。新增目标时同步扩展真实事件 / 原子材料消费、静态任务闭包、协议、Go 校验和测试，不能用动画、查看资料或瞬时缓存状态代替证据。测试由用户运行，验收步骤见 acceptance.md。
