# 开放任务系统

任务无需接受，可以任意顺序完成；推荐顺序为 `docs/quests.json` 的数组顺序。中央“工厂”页签右侧是“任务”；待完成包含未达成和已达成待领奖，已完成仅列已领取奖励的任务。达到后永久保留，安装、消耗、拆除设备不会撤回；进入后续阶段仍可领取前期任务奖励。

## 判定、领奖与存档

- `obtain_item` 使用永久获得记录 / 制造记录，当前只支持首次获得（count=1），不要求道具仍在仓库。制造到机器产物缓存也算获得，但查看图鉴 / 切换配方不算。
- `workshop_recipe` 使用实际工作室批次数；只在成功交付单批产物时加一。开工、取消、暂停、满产物上限等待和地图机器执行同配方都不计数。每种已完成工作室配方的批次数有安全整数上限，支持以后配置累计批次任务。
- `industry.quests` 只存在于主厂：completed / claimed 唯一 ID 数组和 workshop_batches 配方计数。完整本机 / 云存档、增量快照携带同一账本；其他厂区仅投影显示，无副本。旧档缺字段时补空账本并用已有获得证据补认设备任务。无法证明旧工作室配方历史，因此第一项需更新后再完成一批 R1001。
- `claim_quest` 是 Worker 世界操作，在克隆后的完整世界中校验任务已达成且未领取，然后将全部奖励加入起始厂仓库、记录 claimed。同一世界串行处理，重复领取或任一奖励溢出则整笔拒绝。可在任何厂区查看 / 领奖，奖励不会进入当前分厂；查看任务不改变库存，奖励不计入 crafted、生产统计、制造解锁或行业里程碑。
- 新的达成事件由主线程运行时对确认快照作差，按顺序显示每条 3 秒的底部气泡，不阻止编辑；气泡关闭不影响未领奖红点。通知最多保留最近 20 条，仅是本次会话的展示数据，不写存档。首次读取的补认和主动云恢复不重播历史通知；红点仍显示实际待领取状态。
- 客户端与 Go 校验已知任务 / 配方编号、唯一数组、claimed 是 completed 子集、整型计数与大小边界；拒绝 null / 未知字段。服务端继续只校验存档结构，不证明单人任务真实性，无新数据库迁移。

## 后续扩展

在 `docs/quests.json` 追加稳定 ID、阶段、标题、说明、目标及奖励。获得目标与奖励使用现有物品全名（包括“设备·”前缀），工作室目标使用小写配方 ID；`npm run import:gameplay` 解析为运行 ID 并生成目录，不能手改生成的 definitions.json，也不修改原始 v0.9 设计案。既有 ID 不复用、不移除，已有领奖记录不因更新配置再次发奖。任务奖励不作为工业静态闭包的可用材料。

自动化产量、提交指定材料与阶段终极任务尚未实现。增加这些目标时需同步扩展运行层真实事件 / 原子材料消费、协议类型、Go 结构校验和对应测试，不能用动画、查看资料或瞬时缓存状态代替自动化证据。测试由用户运行，验收步骤见 acceptance.md。
