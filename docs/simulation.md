# 生产、库存与物流

## 本轮设计与实现顺序

从静态编辑器扩展为闭环自动化：定义容量 / 配方 → 纯 Go 单刻规则 → SQLite 兼容存档与在线时钟 → 前端库存 / 物流 / 仓库面板 → 测试代码与用户验收。

保持现有工厂大小、编辑交互和账号。没有建造费用，便于自由试验布局；现有机器在服务器启动后自动开始工作。

中心固定建筑现名“工厂仓库”，地图代号 WH；内部定义 id、building_type 和 icon 继续使用 bus。仅更新名称与描述，已有实例、库存、入库和固定建筑保护均保持，无新迁移。

## 时间和配方

服务器每 1000ms 推进一刻，目标 1 TPS。1 tick = 1 秒；生产、端口和带上物品都只按整秒结算。浏览器请求不推进时间；客户端仅补间 / 预演动画，不能补算产量。

| 建筑       | 输入     | 产物     | 时长          |
| ---------- | -------- | -------- | ------------- |
| 采矿机 MIN | 无       | 1 铁矿石 | 1 tick / 1 秒 |
| 熔炉 FUR   | 1 铁矿石 | 1 铁板   | 4 tick / 4 秒 |
| 装配机 ASM | 1 铁板   | 1 齿轮   | 8 tick / 8 秒 |

配方在 catalog JSON 中定义 duration_ms，须至少 1000ms 且为 1000ms 的整数倍（不足一秒或非整秒配置直接拒绝）。当前每种生产机器一个自动配方。之前仅展示的铁板 / 齿轮配方已改为此表，装配机现在消耗 1 铁板。

有原料且产物有空间才推进进度；完成时一次扣除输入、放入产物并清零进度。原料保留在输入格直到完成，其他机器和端口不能从输入格取出。产物满则暂停，无丢弃 / 溢出；腾出空间后继续。产物满时不会不断累计超额生产进度。

## 库存和白名单

生产机器输入、产物各 4 格；每格最多 100，同类物品只占用一个格子。因此铁矿石已达 100 时不能再开第二个铁矿石格。空栈移除后格子可重用。

- 矿机不接受输入。
- 熔炉仅接受 iron_ore。
- 装配机仅接受 iron_plate。
- 产物格不能作为外部输入目标。

默认容量写在建筑定义，同时由服务端规则约束。物流设施使用专用容量：传送带 1 件；端口不缓存物品，直接转移；工厂仓库 直接累计至总仓库。它们不使用机器的 4×100 缓冲格。

## 方向和端口

0° 向右，90° 向下，180° 向左，270° 向上；工厂坐标 Y 向上。OUT 和 IN 均为占一格的定向转移器：

`后方相邻来源 → 端口所在格 → 前方相邻目标`

- 来源：矿机 / 熔炉 / 装配机的产物格，或移动进度已达 1 的传送带。
- 目标：通过白名单的机器输入格、传送带或 工厂仓库。
- 每成功转移一件，冷却 1 tick，最快每秒一件；无来源、目标为空 / 满载或白名单拒绝时不扣物品。
- 两种端口采用同一规则。OUT 常用于机器输出，IN 常用于机器输入，玩家可自由混用；端口不能串联成无延迟链。
- 直接相邻的机器不会自行传料。机器与传送带之间必须经过一个 OUT / IN。

白名单拒绝时，端口显示“目标白名单拒绝”，物品仍在来源。多个端口争用同一来源时不会重复拿取；同一目标传送带每刻只能接收一件。

## 传送带与阻塞

每格仅容纳一个物品，进入时进度为 0，此后每刻 +1，到 1 后尝试转移至箭头方向的下一格。可进入下一条传送带或 工厂仓库；机器输入需要 IN / OUT 端口从带上提取。

传送带可从后方或侧面接收，因此可转弯 / 汇入；面对面反向的两条传送带不会自动互相交接。定向端口可从侧面取物品。不同朝向处目前保留各自视觉，不增加弯角素材。

下游占用且无法移走时，物品停在进度 1，阻塞向上游传播。先完成占用依赖规划，再同时移走旧物品并放入新物品，因此连续带链每秒可以推进一格；不会因遍历顺序让同一物品越过多格。满载闭合环可以同时循环；竞争分支按稳定排序和 tick 轮换，优先顺序可变化。

当前公平策略不承诺复杂网络的最大吞吐量；被阻塞的候选会在后续 tick 重试，不会丢弃物品。

## 总仓库与拆除

物品经传送带或端口送入中心 工厂仓库 后，直接计入玩家总仓库。总仓库按物品累计，不使用 4×100 机器格，暂时只存入和查看，不提供取出 / 投料。玩家之间隔离。

拆除建筑时，其输入、产物和带上物品原子回收入仓库。未完成配方只返还仍在输入格的原料，不凭进度生成产物。移动 / 旋转保留 ID、配置、物品与生产进度，不通过拆除重建。

## 存档和生命周期

每刻事务保存模拟状态、玩家仓库和 revision；每次成功编辑也增加 revision。服务器在线时所有工厂持续运行，不依赖玩家是否打开页面。服务器关闭期间暂停，无离线收益；重启恢复存档进度，不追赶停机时长。

迁移 004 增加 revision、factory_simulations 和 player_warehouses；迁移 005 将原 10 TPS 状态换算为秒并赋予带上物品稳定 ID。老机器没有模拟记录时初始化为空库存 / 零进度，旧账号、位置、角度、配置和 工厂仓库 保留。

005 保留全部库存与仓库数量；tick 和未完成工作向下取整为秒，冷却向上取整，传送带进度 0～9 换为 0、10 换为 1。旧存档至多回退不足 1 秒的未完成工作，不因升级提前产生物品。旧工作时长换为整秒，迁移重复启动不会再次转换。

## 界面和协议

上方总仓库显示铁矿石、铁板、齿轮数量和已提交 tick。选中机器可看 4 输入格、4 产物格、白名单、进度和状态；选中端口可看来源、目标坐标；传送带上显示携带物品，堵塞时停住。

FactoryDetail.simulation 包含 tick、tick_rate、按建筑 ID 映射的 buildings、warehouse 和 transfers；MachineState 包含 input / output、progress / duration、cooldown、status 和可选 belt。belt 新增稳定 id，物品跨带或经端口转移时保持不变。进度与冷却单位均为秒 tick，前端动画细节见 [animation.md](animation.md)。所有生产状态只读，通过现有工厂 GET / 编辑响应返回，无新库存写入端点。

transfers 是最近 3 tick 成功端口转移 / 带到 工厂仓库 的视觉收据，含事件 id、payload_id、item、tick、来源 / 目标 / 可选端口的 ID / 类型 / 位置 / 朝向。只在统一扣除与接收成功后生成；堵塞、满载、白名单拒绝没有新事件。普通带间交接不额外记录。该字段不作为库存或生产依据，客户端不得据此二次结算数量。移动 / 旋转 / 删除使相关旧路线失效；旧 JSON 没有此字段时视为空，无需新迁移。

具体结构以 [openapi.yaml](openapi.yaml) 为准。前端用 revision 拒绝过期响应，协议新增字段暂设为可选以兼容旧测试 fixture；当前服务器始终返回它们。
