# 物流玩法调整

## 实施顺序与范围

本轮在现有 2 TPS / 半秒时基上依次调整投料、垃圾来源、载荷标注、现场移动和地下端口配方。不增加独立时钟、数据库迁移或玩法存档字段，原案 JSON 保持。

| 顺序 | 改动                                            | 规则边界                                                                                          |
| ---- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 1    | 自动投料机 `feeder` 每批最多 20 件、默认 0.5 秒 | 已显式保存的间隔保留；实际批量受来源、过滤、目标剩余空间及带容量限制。其他投料臂 / 分流器规格保持 |
| 2    | 垃圾提取口开放到所有厂区，移除阶段数量上限      | 仍位于各厂顶部 y=10，仍消耗一个初阶自动投料机；占格、真实材料和安全返程约束保持                   |
| 3    | 120% 起显示带上堆叠数量                         | 跟随载荷、固定屏幕 12px、只读真实数量；缩小时不渲染数字，离开带后的吸收动画不显示数字             |
| 4    | 机器人和流体每半秒移动一格                      | 机器人每格仍耗 1 kJ，装卸 / 作业和跨厂工时保持秒级；流体每半秒执行原批次，泵保持 5 kW             |
| 5    | 地下端口配方改为简易齿轮 2、基础铁板 2          | `web_underground_belt`、`d0001`、12 秒产一套、配对和回收保持                                      |

## 投料与多厂垃圾来源

`scripts/import-gameplay.mjs` 生成 `feeder.batch_size=20`；`local/transportConfig.ts` 仅对未配置间隔的 `feeder` 返回 0.5 秒，其他端口仍沿用原默认值。无需写入新配置字段或清空既有冷却；旧档已有显式间隔继续生效。GUI 的“每批最多”直接读取目录，Worker 在同一原子规划中按真实容量截断，失败不扣库存。例如满批 20 件接初阶带时最多接收 2 件；机器某输入已有 95 件时最多再补 5 件。

后续取带修复已将投料间隔和带内行程解耦：半秒投料不再等待初阶带走完整格，主动取货先于带自行出料，来源竞争不误报下游阻塞。取货当刻扣收，动画不占用下一批机会，详见 [取带时序与状态](simulation.md#投料机取带时序与状态)。

提取口保持每 10 秒产 12 包、满产物格时暂停。移除 `placement.ts`、`world.ts`、`construction.ts` 和 `state.ts` 的阶段数量 / 起始厂限制；Go `save.go` / `construction.go` 同步允许分厂与超过旧配额的实例、施工蓝图。阶段上限仍适用于厂区扩建和仓库终端，不受本次提取口改动影响。

所有厂区仍共用唯一总仓库；提取口产物位于所在厂的真实输出缓存，需要本厂物流运回 WH。不会因为切厂或读档自动增加垃圾、设备或并行工作室队列。

## 堆叠数量与绘制开销

`FactoryEditor` 仅向 `ConveyorItemsLayer` 传递 zoom，平移不增加这个组件的属性变化。数字从当前 `belt.payload.count ?? 1` 读取，和图标处于同一载荷节点下，因此直接继承既有 `translate3d`，不另算轨迹、不另设 RAF、不逐帧更新 React 状态。

缩放达到工具栏显示的 120% 时，每个带载荷最多增加一个文本 span；100 件仍是一张图标和一个数字，不按件生成 DOM。数量在确认快照变化时更新，载荷 ID、图标和运动轨迹保持。物品组件 memo 化；zoom 只在父层更新反向缩放 CSS 变量，使数字实际保持 12px，不随地图放大或缩成微小文字。低于门槛直接省略数字节点。

数字位于图标下方，白字深底、不响应指针，不影响地图布局、选取、相机或物料计数。仅在真实带载荷存在时显示；进入机器 / 仓库后数字移除，避免吸收缩放把文字缩小，也避免把视觉尾迹误当作仍在带上的库存。

## 机器人与流体时序

`stepFreight` 每基础 tick 调用，实际行走分支每次最多移动一格、支付 1 kJ；优先级、占格、不可交换位置、路线保护和返程储能估算保持。每秒可走两格意味着持续行走最多耗 2 kJ/s，不能凭提速多获能量。路径费用仍按格计算，无需迁移储能或重估成半价。

装卸准备、巡检、维修、施工、冷却和跨厂过境继续在世界秒级动作点推进；既有整数 `action_ticks` / `work_progress` / `remaining_ticks` 字段仍表达秒级行动。装卸不与同次移动一起完成，跨厂行程保持 8 秒、每秒 1 kJ；机器人补能的 kW、88% 效率和站点共享预算保持。没有新移动相位字段或旧存档分支。

`transferFluids` 每半秒执行一次统一预留与扣收。`fluid_rate` / 容器容量数值保持，含义为每次动作最大整单位数，因此理论每秒流量为原来的两倍；GUI 明确标为“每 0.5 秒流量上限”。新到介质不能同刻跨两格，单介质、满容、权重等待和守恒规则保持。WH 流体输出面仍每秒最多 1 u，使用交替整数预算，不能被两个半秒动作重复提款。

泵每半秒申请并消费实际 2.5 kJ，额定功率仍为 5 kW，供能不足时保留内容；删掉先前等待整秒流体动作的特殊供能分支。其他生产配方、燃料 / 电池功率预算和在线暂停不变。

## 配方与兼容

地下端口材料只修改导入脚本，再运行 `npm run import:gameplay`；运行目录、来源查询和手工 / 地图加工共用新配方。原始 v0.9 设计、物品 / 建筑 ID 和制造工时不改。开发期配方直接生效，不维护并行旧配方或补发材料。

现有有效世界可继续读取，保留实体、库存、载荷 ID、队列和机器人储能；不增加存档 / 数据库版本。更宽松的源头校验同时用于本机和云备份，移动 / 拆除仍按既有原子回收。运行验证状态见 [progress.md](progress.md)。

## 用户验收

由用户执行 `npm test`，再用 `npm run dev` 启动前后端，进行以下检查：

1. 新放自动投料机，间隔默认 0.5 秒、每批上限显示 20。箱 → 投料机 → 箱准备 60 件，连续三个半秒动作各送 20 件；改为 1 / 1.5 秒后保留所选值，刷新仍保持。20 件接初阶带最多送 2；目标满、拒收、缺货不扣来源。
2. P1 在起始厂和一个分厂分别安装多个提取口，均可成功且实际扣道具；顶部以外仍拒绝。10 秒后各自产 12 包，不自动入总仓。分厂选配方、切换、移动、回收、本机刷新和云备份恢复都保持真实数量。
3. 地图缩放 119% / 120% / 200%，检查数量分别隐藏 / 出现 / 仍为屏幕 12px。观察 1 / 2 / 20 / 100 件、拆批、拐弯、满环、堵塞 / 断能和暂停：数字与图标一起移动，数量只随确认状态变化，进入机器 / WH 后不残留。拖动 / 选取 / F 沉浸保持；普通 / 节能无新增持续 RAF。
4. 给真实机器人派一条至少 4 格的畅通路线，正常 2 TPS 下每 0.5 秒移动一格、每格扣 1 kJ。堵塞不移动不扣行走能量；装卸、巡检 / 维修、施工保持原行动工时，跨厂仍为 8 秒。携货取消和低能量必须实际返仓 / 返站，不能瞬移退货。
5. 准备管 → 管 → 储罐，每半秒最多移动一格，不能一刻跨多格；配置和界面按每 0.5 秒批次显示。泵有能时每秒实际花费 5 kJ、断能 / 禁用停止；满容 / 混液 / 加权满分支等待保持，总量守恒。
6. P2 查看 / 制造地下端口，输入仅为简易齿轮 2、基础铁板 2；地图 12 秒 / 工作室 6 秒产一套，安装、两端回收与缓存数量保持。

自动回归代码包括 `logisticsUpgrade.test.ts`、`simulationTime.test.ts`、`ConveyorItemsLayer.test.tsx`、既有物流 / 流体 / 机器人场景，以及 Go 的分厂源头蓝图与云备份读写校验。静态检查和编译不代表这些测试或浏览器 / 性能验收已执行。
